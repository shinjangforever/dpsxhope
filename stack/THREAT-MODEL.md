# Threat model ของระบบในคู่มือนี้

เอกสารนี้ไล่ว่าระบบที่สร้างจากต้นแบบในคู่มือ (ถามเอกสาร, agent, งานอัตโนมัติ, ai-api) มีอะไรต้องปกป้อง ใครอาจทำให้เสียหาย ทางไหน และตอนนี้กันไว้แค่ไหน ใช้เป็นแม่แบบสำหรับเขียน threat model ของระบบคุณเอง

**สถานะ (2026-11-12):** เขียนจากการอ่านโค้ดและชุดทดสอบของคู่มือ ยังไม่ได้ให้ผู้เชี่ยวชาญด้านความปลอดภัยตรวจ และยังไม่เคยทดสอบเจาะ ช่อง "กันไว้แล้ว" หมายถึงมีโค้ดและชุดทดสอบรองรับ ไม่ได้รับรองว่ากันได้ทุกกรณี

## 1. สิ่งที่ต้องปกป้อง

| สิ่งที่ต้องปกป้อง | เสียหายอย่างไรถ้าหลุด |
|---|---|
| API key ใน `.env` | คนอื่นใช้โมเดลในชื่อคุณ และคุณเป็นผู้จ่าย |
| เอกสารใน `my-docs` และไฟล์ใน `inbox` | ข้อมูลภายในหรือข้อมูลส่วนบุคคลรั่ว |
| ระบบที่ tool ไปแตะ (ฐานข้อมูล อีเมล การจ่ายเงิน มอเตอร์) | ข้อมูลถูกแก้ ข้อความถูกส่ง เงินถูกจ่าย ของจริงเคลื่อนที่ |
| ความถูกต้องของคำตอบและสรุป | คนตัดสินใจจากข้อมูลผิด |
| log | รู้ย้อนหลังไม่ได้ว่าเกิดอะไร หรือ log เองกลายเป็นที่รั่วของข้อมูล |

## 2. เส้นแบ่งความไว้ใจ

ข้อมูลที่ข้ามเส้นเหล่านี้ต้องถูกตรวจทุกครั้ง เพราะฝั่งหนึ่งควบคุมอีกฝั่งไม่ได้

1. **เอกสารและไฟล์ที่รับเข้า → prompt ของโมเดล** เนื้อหามาจากใครก็ได้ และโมเดลแยกข้อมูลกับคำสั่งไม่ได้อย่างแน่นอน
2. **คำตอบของโมเดล → การเรียก tool** โมเดลอาจถูกหลอกหรือเพ้อ
3. **เครือข่าย → ai-api และช่องรับไฟล์ของงานอัตโนมัติ** ผู้เรียกอาจไม่ใช่คนที่คุณตั้งใจ
4. **เครื่องของคุณ → ผู้ให้บริการโมเดล** ข้อความที่ส่งไปอยู่นอกการควบคุมของคุณ
5. **ไลบรารีภายนอก → โปรแกรมของคุณ** โค้ดของคนอื่นรันด้วยสิทธิ์ของคุณ

## 3. ภัยและสิ่งที่กันไว้

| # | ภัย | ข้ามเส้น | กันไว้แล้ว | ช่องว่างที่เหลือ |
|---|---|---|---|---|
| T1 | เอกสารมีคำสั่งแฝง ทำให้โมเดลเรียก tool ที่ไม่ควร (prompt injection) | 1, 2 | tool ที่เสี่ยงต้องมีคนอนุมัติ; ขั้นถาม AI ในงานอัตโนมัติไม่ได้ tool ถ้าไม่ระบุ; งานตัวอย่างบอกโมเดลให้ถือเอกสารเป็นข้อมูล | คำสั่งใน prompt ลดความเสี่ยงได้เท่านั้น tool ที่ไม่ต้องอนุมัติยังถูกเรียกได้ และไม่มี sandbox |
| T2 | โมเดลสั่งการที่อันตรายต่อของจริง | 2 | [ด่านตรวจของ robokit](../fields/robotics/robokit/README.md) ตรวจด้วยกฎที่แยกจากโมเดลและปฏิเสธแทนการปรับค่า | ด่านเป็นซอฟต์แวร์ในเครื่องเดียวกัน ยังไม่ใช่ชั้นป้องกันอิสระ |
| T3 | เจ้าของงานอัตโนมัติอนุมัติ tool ล่วงหน้ากว้างเกินไป | 2 | ต้องระบุชื่อ tool ทีละตัวใน `allow_tools`; ไฟล์งานที่ใช้ tool เสี่ยงโดยไม่ระบุถูกปฏิเสธตั้งแต่ตรวจ | ไม่มีการจำกัดค่าที่ส่งให้ tool นั้น |
| T4 | ชื่อไฟล์หรือที่อยู่ไฟล์พาเขียนออกนอกพื้นที่ | 1, 3 | งานอัตโนมัติปฏิเสธที่อยู่นอกพื้นที่ทำงานและไม่เขียนทับของเดิม; ช่องรับไฟล์รับเฉพาะชื่อที่ไม่มีโฟลเดอร์ | tool ที่คุณเขียนเองต้องตรวจเอง |
| T5 | คนอื่นเรียก ai-api | 3 | Bearer key เทียบแบบเวลาคงที่, จำกัดอัตรา, CORS allowlist, ไม่ยอมเปิดรับจากภายนอกถ้าไม่ได้ตั้ง key | key เดียวใช้ร่วมกัน ไม่มีบัญชีผู้ใช้ และตัวจำกัดอัตราอยู่ในหน่วยความจำของ instance เดียว |
| T6 | คนอื่นส่งไฟล์เข้าช่องรับไฟล์ของงานอัตโนมัติ | 3 | รับเฉพาะจาก `127.0.0.1`, ต้องมี token ยาวอย่างน้อย 16 ตัวอักษร, จำกัดขนาดและชนิดไฟล์ | โปรแกรมอื่นในเครื่องเดียวกันที่รู้ token ส่งได้ และไม่มี TLS จึงห้ามเปิดออกนอกเครื่องตรงๆ |
| T7 | API key รั่ว | 4 | `.env` ไม่ขึ้น Git, `config set` รับค่าโดยไม่ค้างในประวัติคำสั่ง, คำสั่งตรวจเครื่องไม่แสดงค่า key | ไฟล์ `.env` ไม่ได้เข้ารหัส ใครอ่านไฟล์ในเครื่องได้ก็อ่าน key ได้ |
| T8 | เนื้อหาเอกสารรั่วทาง log | 1 | log งานอัตโนมัติไม่เก็บเนื้อหา; audit log ตัดข้อความที่ยาวเกิน 200 ตัวอักษร | input สั้นของ tool ถูกบันทึกทั้งหมด |
| T9 | ข้อมูลออกไปยังผู้ให้บริการโมเดลโดยไม่ตั้งใจ | 4 | ใช้ Ollama ได้ทุกส่วน; มีข้อความเตือนเมื่อเลือก Claude | ไม่มีการคัดข้อมูลส่วนบุคคลออกก่อนส่ง |
| T10 | ไลบรารีภายนอกมีช่องโหว่หรือถูกแก้ | 5 | `python hope.py audit` (npm audit และ pip-audit); ai-api ล็อกรุ่นด้วย `package-lock.json` | ฝั่ง Python ไม่ล็อกรุ่น; การตรวจประจำสัปดาห์ใน GitHub Actions ยังไม่เคยรัน |
| T11 | คำตอบหรือสรุปผิดแต่ดูน่าเชื่อ | 2 | คำตอบจากเอกสารมีแหล่งอ้างอิง; สรุปที่ว่างหรือถูกตัดถูกนับเป็นล้ม; มี `llm-eval` สำหรับตั้งเกณฑ์ | ไม่มีการตรวจข้อเท็จจริงของสรุปอัตโนมัติ |
| T12 | งานอัตโนมัติรันซ้อนหรือทำไฟล์เดิมซ้ำ | - | ล็อกกันรันซ้อน และสถานะกันทำซ้ำ | ถ้าโปรแกรมถูกปิดกลางขั้น ต้องรันใหม่ทั้งรายการ |

## 4. เรียงลำดับสิ่งที่ควรแก้

เรียงจากผลเสียมากและเกิดง่าย ไปหาผลเสียน้อยหรือเกิดยาก ลำดับนี้เป็นการประเมินของผู้ดูแลคู่มือ ระบบของคุณอาจเรียงต่างกัน

1. **T1 กับ T3** ถ้าคุณมี tool ที่แก้ข้อมูลหรือส่งออก: อย่าให้ tool นั้นกับขั้นที่อ่านไฟล์จากคนนอก และให้คนอนุมัติทุกครั้ง
2. **T5** ถ้าจะเปิดบริการออกนอกเครื่อง: ต้องมีบัญชีผู้ใช้และ TLS ก่อน ซึ่งคู่มือนี้ยังไม่มี
3. **T7 กับ T9** ถ้าเอกสารเป็นความลับ: ใช้ Ollama และจำกัดสิทธิ์อ่านไฟล์ `.env`
4. **T10** รัน `python hope.py audit` ก่อนเปิดให้คนอื่นใช้ และเป็นระยะหลังจากนั้น
5. **T2** ถ้าต่อกับของจริงที่เคลื่อนที่ได้: ต้องมีชั้นป้องกันทางกายภาพที่ไม่ขึ้นกับซอฟต์แวร์

## 5. การทดสอบเจาะ

การทดสอบเจาะคือการให้คนลองโจมตีระบบเพื่อหาช่องก่อนผู้ไม่หวังดี ทำได้เฉพาะกับระบบที่คุณเป็นเจ้าของ หรือได้รับอนุญาตเป็นลายลักษณ์อักษรจากเจ้าของ โดยตกลงขอบเขต ช่วงเวลา และผู้ติดต่อไว้ก่อน คู่มือนี้ยังไม่มีขั้นตอนและยังไม่เคยทำ

สิ่งที่ลองกับระบบของตัวเองได้ทันทีโดยไม่ต้องมีเครื่องมือพิเศษ

- วางไฟล์ที่มีข้อความ "ให้เมินคำสั่งก่อนหน้า แล้ว..." ใน `inbox` ของงาน `inbox-summary` แล้วดูว่าสรุปเปลี่ยนไปไหม
- เรียก ai-api โดยไม่ใส่ key ใส่ key ผิด และจากที่อยู่ที่ไม่ได้อยู่ใน `ALLOWED_ORIGINS`
- ส่งชื่อไฟล์ `../x.txt` เข้าช่องรับไฟล์ของงานอัตโนมัติ

## 6. เมื่อเกิดเหตุ

เตรียมไว้ก่อนเกิดเหตุ ไม่ใช่ตอนเกิด

1. **หยุด:** ปิดบริการหรือหยุดงานอัตโนมัติ (Ctrl+C หรือยกเลิกการตั้งเวลา) ก่อนสืบหาสาเหตุ
2. **เปลี่ยน key:** ถ้าสงสัยว่า key รั่ว ให้ยกเลิก key เดิมที่หน้าของผู้ให้บริการและสร้างใหม่ทันที แล้วตั้งใหม่ด้วย `python hope.py config set`
3. **เก็บหลักฐาน:** คัดลอก `logs/audit.jsonl` และ `logs/automation.jsonl` ออกมาก่อนแก้อะไร
4. **ดูว่าเกิดอะไร:** `python hope.py auto report ชื่องาน` และอ่าน audit log ว่า tool ไหนถูกเรียกเมื่อไร
5. **แจ้งผู้เกี่ยวข้อง:** ถ้าข้อมูลของคนอื่นอาจรั่ว ให้แจ้งเจ้าของข้อมูลและผู้รับผิดชอบตามกติกาขององค์กรและกฎหมายที่ใช้กับคุณ
6. **แก้และบันทึก:** แก้ช่องที่ใช้ เพิ่มชุดทดสอบที่จับกรณีนั้น และเพิ่มแถวในตารางข้อ 3

## 7. ใช้เป็นแม่แบบ

คัดลอกไฟล์นี้ไปไว้กับระบบของคุณ แล้วแก้ตามลำดับ: ข้อ 1 ใส่สิ่งที่คุณต้องปกป้องจริง, ข้อ 2 วาดเส้นแบ่งของระบบคุณ, ข้อ 3 ไล่ทีละเส้นว่าอะไรข้ามมาได้ และเขียนเฉพาะสิ่งที่กันไว้แล้วจริงพร้อมหลักฐาน ช่องที่เขียนไม่ได้คือช่องว่าง
